# Graph 0.5 매뉴얼 설계

## 배경

`bluetape4k-graph`는 그래프 모델과 동기·코루틴 API, 다섯 개 백엔드, graph-io, Ktor, Spring Boot, 벤치마크, 예제를 함께 제공한다. 현재 README와 예제 문서는 풍부하지만 독자가 “어떤 API와 백엔드를 선택하고, 어떤 순서로 학습하며, 운영에서 무엇을 확인해야 하는가”를 한 흐름으로 읽을 수 있는 버전 고정 매뉴얼은 없다.

이 매뉴얼은 README를 확장한 소개 문서가 아니라 Graph 0.5 사용 계약의 기준 문서다. 작성 원본은 이 저장소의 `docs/manual/`에 두고, 웹사이트는 검증된 snapshot만 게시한다.

## 릴리스 경계

- 공개 minor 버전: `0.5`
- 안정 릴리스: `0.5.1`
- 릴리스 커밋: `3e0fa7cb9e3bc70c2743aeebda2487f3e45e4907`
- 작성 기준: 매뉴얼 PR이 병합된 `develop` 커밋
- 소비자 버전 기준: `bluetape4k-dependencies` 한 개
- 릴리스 inventory: 라이브러리/BOM 15개, 벤치마크 4개, 예제 12개

0.5.1 이후에만 존재하는 API나 이슈 #310~#317의 예정 기능은 안정판 기능으로 설명하지 않는다. Neptune은 0.5.1에서 지원하지 않으며, 선택 가이드에서 미지원 경계와 이유만 밝힌다.

## 검토한 접근

### 1. README 조합형

기존 README를 웹사이트에 그대로 연결하거나 짧게 재구성한다. 빠르지만 선택 기준, 실패 계약, 운영 지표, 학습 순서가 흩어지고 README가 매뉴얼의 사실상 원본이 된다. 이번 목표와 맞지 않아 채택하지 않는다.

### 2. 저장소 소유 매뉴얼형 — 채택

`docs/manual/`에 영문·한글 원문, manifest, 생성·검증 도구, 다이어그램 원본을 둔다. 웹사이트는 릴리스 provenance와 작성 커밋을 기록한 snapshot을 생성한다. 문서량은 늘지만 버전별 계약, 링크 검증, 양 언어 동등성, 향후 블로그 재사용을 일관되게 관리할 수 있다.

### 3. 웹사이트 직접 작성형

사이트 저장소에서 모든 설명을 작성한다. 사이트 편집은 단순하지만 코드와 문서가 분리되어 API 변경과 릴리스 검증이 늦어진다. source of truth 원칙에 어긋나므로 채택하지 않는다.

## 정보 구조

### 시작과 선택

1. 개요와 저장소 지도
2. `bluetape4k-dependencies` 기반 설치
3. 10분 빠른 시작
4. 학습 경로

### 핵심 모델과 API

- `GraphVertex`, `GraphEdge`, `GraphPath`, `GraphElementId`
- `GraphOperations`와 `GraphSuspendOperations`
- 세션, vertex/edge repository, traversal repository
- `VertexLabel`과 `EdgeLabel` schema DSL
- CRUD, merge/upsert, batch 생성
- `transaction {}`와 `suspendTransaction {}`
- 경로 탐색과 백엔드별 capability 경계

### 백엔드 선택

Neo4j, Memgraph, Apache AGE, TinkerPop/TinkerGraph, FalkorDB를 운영 전제, 질의 언어, 트랜잭션, schema/index, 로컬 검증 방식으로 비교한다. “기능 수가 많은 제품”이 아니라 이미 운영하는 시스템과 필요한 의미론을 기준으로 선택하도록 안내한다.

### graph-io와 통합

- 공통 record/options/path/external-ID 계약
- CSV, Jackson 2/3 NDJSON, GraphML
- 동기, virtual-thread, coroutine 실행 모델
- OkIO Source/Sink, 압축 chain, DAEAD chunk 암복호화
- Ktor `GraphPlugin`
- Spring Boot auto-configuration

### 운영과 증거

- 오류·취소·트랜잭션 경계
- 테스트와 Testcontainers
- 대량 입출력의 메모리·backpressure·파일 보안
- 백엔드 관측 지표와 장애 진단
- 네 개 벤치마크 결과를 읽는 방법과 비교 한계

### 모듈과 학습 경로

- 15개 publishable module마다 좌표, 제공 기능, 핵심 API, 빠른 시작, 선택 기준, 실패 유형, 운영, 테스트, 관련 가이드, 제외 범위를 설명한다.
- 12개 예제마다 해결 문제, 구성, 실행 방법, 관찰 결과, 코드 읽는 순서, 확장 과제, 운영에 그대로 가져가면 안 되는 경계를 설명한다.
- 벤치마크 4개는 라이브러리 모듈처럼 소개하지 않고 의사결정 증거 페이지로 묶는다.

## 문서 소스 구조

```text
docs/manual/
├── manifest.yaml
├── generated/manifest.json
├── en/
│   ├── index.md
│   ├── getting-started.md
│   ├── architecture/
│   ├── backends/
│   ├── graph-io/
│   ├── frameworks/
│   ├── guides/
│   ├── benchmarks/
│   ├── modules/
│   └── examples/
├── ko/                    # 영문과 동일한 route 집합
└── assets/                # editable SVG + canonical 2x PNG
```

manifest는 release ref/commit, 프로젝트 inventory, 언어별 route, 자산, source path를 한곳에서 관리한다. 생성기는 반복되는 구조만 담당하며, API 계약과 선택 설명은 사람이 검토 가능한 Markdown 원문으로 유지한다.

## 다이어그램

다음 다섯 개를 현재 매뉴얼의 dark visual family로 새로 만든다.

1. repository learning map
2. core abstraction map
3. backend decision map
4. graph-io pipeline
5. framework request/integration flow

모든 SVG는 card bounds, 4px 이상 connector, 의미별 대비 색상, 14x14 arrowhead, rounded `Q` bend, 접근 가능한 title/description을 갖는다. CairoSVG로 3200x2080 PNG를 생성하고 connector, geometry, endpoint, mixed-corner 감사를 통과한 뒤 원본 크기로 눈 검수한다. 기존 `.dot`, `.plain`, `*-sketch.svg`는 정보 참고 자료일 뿐 최종 자산으로 복사하지 않는다.

## 한국어 품질

한글 문서는 영문 문장 순서를 그대로 옮기지 않는다. API 이름과 표준 기술 용어는 보존하되 일반 명사는 자연스러운 한글로 쓴다. 각 페이지는 독자가 선택하고 실행하고 진단하는 흐름으로 교정한다. 생성기 공통 문구도 먼저 한글 품질을 고정한 뒤 문서를 생성한다.

## 검증 계약

- 태그 `0.5.1`이 지정 커밋으로 해석되는지 확인한다.
- release tree에서 31개 프로젝트 inventory를 추출하고 15/4/12 분류를 고정한다.
- manifest와 실제 영문·한글 route가 정확히 일치해야 한다.
- 모든 source link와 내부 link가 0.5.1 경계에서 존재해야 한다.
- 생성기·manifest·release contract 테스트를 실행한다.
- 다섯 diagram pair의 크기, 접근성, marker, connector geometry를 검사한다.
- `git diff --check`와 문서 범위에 맞는 compile-only CI를 통과한다.
- 병합 후 사이트 snapshot 테스트, Astro build, 배포, 공개 route와 자산 hash를 검증한다.

## 작업 분리

- 공통 계약과 개요·핵심·선택 가이드
- 15개 module 페이지
- 12개 example 및 benchmark 페이지
- 다이어그램과 최종 통합·검증

각 영역은 파일 소유권을 분리해 병렬 작성한다. 공통 manifest와 index, 검증 도구, 최종 문장 교정은 통합 담당자가 책임진다.

## 완료 조건

매뉴얼은 README보다 상세해야 하며, 코드 사용법뿐 아니라 선택 기준·실패 계약·운영·테스트·학습 순서를 제공해야 한다. Graph 0.5.1에 없는 기능을 현재 계약처럼 설명하지 않고, 영문과 한글 route가 완전히 대응하며, 다이어그램과 공개 웹 snapshot까지 검증돼야 완료다.
